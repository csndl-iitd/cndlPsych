## 2026-10-01 - M0 repo and tooling

- **Python build/validate ported to Node and deleted.** `spec/tools/build.py`, `validate.py`, `yaml12.py` are replaced by `build.js`, `validate.test.js`, `yaml12.js`. `build.js` output was compared with the Python output byte for byte (all 14 files, LF endings) before deletion. `build.js --check` (`npm run check:schemas`) fails when `spec/schema/` is stale. `chunks.py` and `gen_rules.py` stay as the references for M7.
- **`chunks.js` added now** (not in M7) because the validator's Firestore section needs the codec. It is a tooling port only; the runtime codec in `storage/` is still M7. Parity is by round trip, not by bytes: Python `json.dumps` writes `1.0` where JS writes `1`, and gzip headers can differ, so M7 must decide what "identical" means for the shared fixture.
- **js-yaml 4 with `CORE_SCHEMA` + the merge type.** The core schema is YAML 1.2 (`on` stays a string, `16:9` stays a string); the sources use `<<` merge keys, which the core schema omits. js-yaml is pinned to major 4 (npm now resolves 5).
- **Ajv strict mode on, except `strictTypes` and `strictRequired`.** Those two police style (`pattern` without `type`, `required` of a property defined in a sibling subschema) that the schemas use on purpose. Unknown keywords still fail.
- **`.gitattributes` forces LF.** The Python reference wrote CRLF on Windows when run in place; generated files must not depend on the OS.
- **Layer rules are enforced twice**: `eslint.config.js` (`no-restricted-imports`, `no-restricted-syntax` for dynamic SDK imports, storage/random globals) and `tools/check-layers.js` (CI; also sees dynamic imports and `export ... from`). Both are tested with deliberately bad imports. `foundation` may import its own siblings (`./x.js`) but nothing else.
- **Test naming:** Vitest `*.test.js`, Playwright `*.e2e.js`, both beside the code.
- **`tsc` scope** is `spec/types.d.ts` plus `spec/examples/custom/**`; framework code is added to `tsconfig.json` as it is written.
- `esbuild` is installed but has no script yet; the first bundle is built when there is something to bundle (M4/M10).

- Playwright ran Chromium only (desktop and Pixel 7 emulation). WebKit, Firefox and real phones are untested.

## 2026-10-01 - M1 compiler and cascade

- **`compile(project)` is pure.** `framework/authoring/compiler.js` takes file texts, the generated schemas, the custom-module manifests (default exports with functions dropped) and an asset list, and returns `{plan, diagnostics}`. File access lives in `cli/project.js`, so the same compiler can run in the browser and the VS Code extension. Diagnostics carry `code`, `file`, YAML `path` (`blocks[5].input.profiles.phone.rules[1]`) and a message; there are no line numbers yet (except for YAML syntax errors).
- **Resolution is per concrete profile.** For each profile a block runs on, every cascade level applies `"*"` first, then the profile. A later level wins over an earlier one whatever its profile specificity (a block-level `"*"` binding replaces an experiment-level `phone` binding). A `disable` under one profile key only affects that profile. The plan holds one resolved scope per profile for each block and each `response_task` trial; triggers are profile independent.
- **Framework defaults** (cascade level 0, `defaults.js`): gestures `[tap]`, `fire_on: up`, cursor autohide 1000 ms / 3 px, `show_zones: false`. The spec does not state these; they are my reading of the schema defaults. Change them there if wrong. `any` and `none` are built-in intents and need no binding.
- **Stimulus triggers** compile to rules `stim:<name>` (`on: phase.onset`, `where: {stimulus: name}`) at the lowest trigger level, for the stimuli a block refers to. `trigger_base` expands to `base + index` (0-based).
- **Coverage** counts a rule that emits the intent as coverage, not only a binding. This is what lets the example's `next` intent work on desktop (rule `space_done`) and phone (rule `two_taps`).
- **New check codes beyond the README list:** `disable-conflict` (a scope that both disables and defines the same id; found by the idempotence property test, because it makes rule order depend on how often the level is applied), `gesture-not-enabled` (a tap/swipe/longpress binding whose gesture is not enabled), `each-name-template`, `task-profile-unsupported`, `block-profile-not-allowed`, `device-fixed-not-allowed`, `consent-file-missing`, `missing-asset`. `keyboard_task` is reported as an unknown module with a pointer to `response_task` (no alias).
- **Deviation to confirm: `mm` / `deg` without calibration is a warning, not an error.** ARCHITECTURE.md section 4 says the compiler errors, but `spec/examples/` (which must compile) uses `12mm` hit padding and `14mm` AprilTags with no `device.calibration`. The example wins; the compiler emits `units-need-calibration` warnings. If the rule should be an error, the example needs a calibration block (a one-line change in `spec/examples/experiment.yaml`).
- **Idempotence property** is tested two ways with a seeded generator (300 random cascades each; no property-testing dependency was added): re-resolving a resolved scope (`resolvedAsScope`) changes nothing, and applying every level twice equals applying it once. Trigger resolution has the second property.
- **`ajv` and `js-yaml` moved to `dependencies`** (the framework imports them). Ajv compiles validators with `new Function`, so a page served with a CSP that forbids `unsafe-eval` cannot run the compiler in the browser; M10 should decide between relaxing the CSP and pre-compiled (standalone) validators. The CLI is not affected.
- **Not covered by the compiler yet:** the design factor cell expansion (`design`, `applies_to` evaluation, `max_run`) happens at run time in M4; M1 only checks that `{factor}` templates and `applies_to` keys refer to real factors. `correct.where` keys are not checked against the context fields.

### M1 not verified

- The cascade semantics for "`*` versus profile across levels" and the framework defaults are my interpretation of `spec/`; no author has confirmed them.
- The golden files (`framework/authoring/golden/`) were generated by the compiler and then read against the spec by hand, not derived independently.
- Nothing has run in a browser; the compiler is only exercised from Node.

## 2026-10-01 - M2 foundation runtime

- **`seq` starts at 0.** ARCHITECTURE.md said "gap-free integer from 1"; `spec/examples/events.sample.jsonl` starts at 0 and the event schema allows 0. Spec wins, ARCHITECTURE.md fixed. A rejected emit (bad envelope or failed dev validation) consumes no seq.
- **Bus delivery order = seq order.** An event emitted from inside a handler is queued and delivered after the current event finishes, so no subscriber ever sees a later seq first. Every handler runs for every event; the first handler error is rethrown after delivery (or passed to `onHandlerError`). `caused_by` is explicit, never inferred.
- **Dev validation is injected, not imported.** `createBus({validate})` takes a function returning problems; foundation imports nothing, so tests and the runtime's dev build pass an Ajv validator over `event.schema.json`. The bus itself always checks the envelope. A test pins `SOURCES` to the generated schema's source enum.
- **`t_bus`** is recorded only when the event reached the bus more than 1 ms after its source time `t` (the spec says "meaningfully"; the threshold is mine).
- **Device detection rules (mine, spec is silent):** `desktop` = fine pointer and hover; `phone` = coarse pointer, touch, shorter screen side <= 599 CSS px; `tablet` = coarse pointer, touch, shorter side >= 600. `min_width_px` / `max_width_px` in `device.profiles.*.when` therefore mean the shorter screen side, so rotating a phone does not change its profile. `keyboard` cannot be detected and is assumed on fine-pointer devices. Custom profiles are tried before the built-ins (they win ties); a custom profile with a built-in id replaces it. If nothing matches, the device is rejected and `device.profile` records `profile: "unknown"`.
- **Rejection path:** `admitDevice` emits `device.profile`, and for a profile that is not in `device.allowed` (or matches nothing) also `session.end {reason: device_rejected}`; the caller shows the message (`rejected_message` or a default). `select: prompt` returns `pending` until an answer is given and emits nothing meanwhile.
- **Consent gate and record:** `createSessionRecord` throws without an accepted consent block, so a record cannot exist before consent. `min_age` is checked separately (`checkAge`) because the age answer is collected after consent; an unknown age fails the check when `min_age` is set.
- **Not in M2 although the foundation list suggests it:** the seeded `rng` of `types.d.ts` (needed by tasks in M4), frame-aligned onset stamping beyond the `nextFrame` helper (M10 measures it), and the subject / session form flow (M4). `session.js` provides ids, URL parameters, seed resolution, the consent gate and the record; the lifecycle that sequences them lives in `runtime/` (M4).
- **Matcher semantics chosen:** ordered sequences ignore non-matching events and are matched greedily (latest-starting partial wins; up to 8 partials are kept when `distinct_by` is set); `unordered` finds a real assignment of distinct events to steps by backtracking, so an event that could fill two steps does not block a match; `min_ms` compares `data.duration_ms`; a `null` condition matches null or missing; `ne` / `not_in` match a missing field; a missing `distinct_by` field is never distinct; `regex` is unanchored, globs are anchored and `*` also matches dots.
- **Browser tests** now start a static server (`tools/static-server.js`) and run three Chromium emulation projects: desktop, phone (Pixel 7) and tablet (Galaxy Tab S4). Layer rules exempt `*.e2e.js` like `*.test.js`.

- Device detection ran only in Chromium emulation. Real phones and tablets (iOS Safari in particular: `pointer`/`hover` media queries, `maxTouchPoints`, screen sizes) are untested, and the 600 px phone/tablet boundary is a convention, not a measurement. A desktop Chromium on this machine reported touch points (touch-screen host) and was still detected as desktop, as designed.
- `clock.js` is only tested with injected time sources and `performance.now()` monotonicity; no timing accuracy is claimed. `nextFrame` is unmeasured.
- `session.js` is not wired to storage or the lifecycle yet, so "nothing is persisted before consent" is enforced at the record level only; the end-to-end check belongs to M4/M6.

## 2026-10-01 - M3 input pipeline and jsPsych bridge

- **jsPsych comes from npm** (`jspsych` 8.3.0, `@jspsych/plugin-html-keyboard-response` 2.2.0, as runtime dependencies; you asked for npm instead of a vendored copy). "Vendored" now means bundled by esbuild into the user-facing folder at M10. `bridge.js` itself imports nothing from jsPsych: jsPsych instantiates the extension and hands itself over.
- **The bridge is made by a factory** (`createBridge({bus})`) because jsPsych does `new Extension(jsPsych)`. Internal keys are `F13`..`F24` in intent-name order (`any` first), or `plugin_key`. A trial enables the extension with `params: {accepted: [intents]}`; the plugin's `choices` are `bridge.keysFor(accepted)` (or `ALL_KEYS` for `any`). `bridge.key_injected.origin_t` is the time of the real input; semantic events are stamped with their cause's `t`, so `semantic.*.t` is the participant's action time, not when the mapping ran.
- **Consumption.** A key press is swallowed (`preventDefault` + `stopImmediatePropagation` in the capture phase, `consumed: true` in the event) when a rule or binding with `consume` (default true) would match it. Because the decision must come before the raw event is emitted, matchers gained `peek()` / `clone()` (state-free look-ahead). Only keys can be swallowed; a consumed tap simply does not also count as `any`. A real key that no rule consumes still reaches jsPsych natively, so `any` with `ALL_KEYS` works for keys without injection; a tap on an `any` trial needs the injected key.
- **What is logged:** every key down/up except while a form field has focus (typed answers are never captured); raw `input.pointer.*` and gestures only while the scope enables at least one gesture; mouse movement without a button is never logged (it only feeds the cursor). Right-click starts no gesture and the context menu is suppressed on the stage.
- **Gesture semantics (mine, spec is silent):** one pointer at a time. Defaults: tap <= 500 ms and <= 10 px; longpress 500 ms, slop 10 px; swipe >= 40 px, >= 0.2 stage lengths/s, <= 1 s; drag slop 10 px. Swipe and drag velocities are in stage lengths per second (the unit of `min_velocity`); `distance`/`dx`/`dy` are CSS px. With `drag` and `swipe` both enabled, drag wins. `fire_on: down` emits the tap at the press (up = down, duration 0). `tap_index` counts taps within 400 ms and 40 px. Tap bindings with `on: down` match the raw `input.pointer.down`; region tests use the tap's down point. Pointer paths are chunked at 256 rows and can be decimated with `hz`.
- **Stage:** coordinates are normalised per axis (x by width, y by height); bare lengths use the shorter side. `mm` without calibration is now an **estimate from the CSS reference pixel (96 px/inch)** with a one-time `system.warning` (`uncalibrated_units`), instead of throwing: the compiler only warns, and the example project uses mm. `deg` still needs `px_per_mm` and `viewing_distance_mm`. Listeners attach to the full-viewport root so taps in the letterbox are seen (`inside_stage: false`).
- **Rule 4 is enforced three ways:** the ESLint `no-restricted-syntax` rule, a grep test over `framework/` and the example custom code, and the browser tests. `ResizeObserver` (stage) and `dispatchEvent` (bridge) are not listeners and are allowed.
- **Rules cannot match `semantic.*` events** (prevents loops). Rule `reset` levels order is trial < block < session (`never` is never reset); `mapping.reset(level)` is for the runtime lifecycle (M4).
- **Browser tests** use an esbuild bundle (`tools/build-e2e.js`, built by the Playwright web server command) that includes the real framework, real unmodified jsPsych, and an Ajv validator that checks every emitted event against the generated schema; page errors fail the test. Touch input on phone/tablet comes from Chromium `Input.dispatchTouchEvent`; desktop uses the Playwright mouse. Both are trusted events; script-generated events are used for the untrusted case.
- **Bug found by tests:** `path_length` / `straightness` ignored the last segment up to the release point.

## 2026-10-01 - M4 built-in modules and lifecycle

- **New dependency (flag): `@jspsych/plugin-survey` 4.0.0** (pulls `survey-core` / `survey-js-ui`). All participant forms (consent, subject, session, `survey` blocks) are survey trials. A hand-written form would need its own DOM listeners, which hard rule 4 reserves for `input.js`. The plugin is a jsPsych plugin, so I treated it as covered by "jsPsych"; say if you want it removed. It needs its stylesheet, which the bundle provides through `boot({styles})`; the e2e bundle imports `survey.css` as text. `html-keyboard-response` shows every stimulus phase.
- **Nothing is recorded before eligibility.** `createBus({recording: false})` drops events (emit returns null, nothing numbered or delivered) until `startRecording()`. The lifecycle runs consent, subject form, session form and the `min_age` check unrecorded, then builds the session record, starts recording and emits `session.start` as seq 0, followed by `session.clock_anchor`, (`system.warning` for debug), `device.profile`, `consent.accepted`, `form.submitted` x2, `stage.resize`. A declined consent or a failed `min_age` therefore leaves no event and no record. A device rejection happens after recording starts, so it is persisted (`device.profile`, `session.end device_rejected`, record status `device_rejected`).
- **Spec change: `phase.onset` gains optional `stimulus_data`** (events catalog, regenerated schema): custom generators return per-trial data (positions, identities) that must reach the log. Nothing else in `spec/` changed.
- **`runtime/memory-store.js`** is the storage used until M6: `begin(record)`, `append(event)`, `finish(record)`. Real stores follow the same contract. `debug.time_scale` is applied to every duration and logs a `system.warning`; the rule "never stored as valid data" is not enforced yet (M6).
- **Rng:** `foundation/rng.js`, mulberry32 with FNV-1a `fork(label)`; forks depend only on seed and label, so adding a trial or stimulus does not shift other draws. The block rng is `createRng(seed).fork("block:<id>:<run>")`, trials fork `trial:<n>`, stimuli `stimulus:<name>:<occurrence>`. The same seed gives the same trial order (browser-tested).
- **response_task semantics (mine where the schema is silent):**
  - Order: without `design`, definition order with each trial repeated; with `design`, `design.repetitions` rounds over the full factorial, trials filtered by `applies_to`; `order: shuffle` (default) shuffles all instances with `max_run` enforced by re-shuffling (error after 1000 attempts), `sequential` keeps the list.
  - A phase is a stimulus plus an optional gap (`<phase>_post`); `post` on a stimulus or trial is a real blank phase with its own `phase.onset/offset` (no stimulus field).
  - Responses are evaluated from `semantic.<intent>` bus events, never from jsPsych data. `response.evaluated` carries `rt_ms` from the phase onset. A response outside a matching `correct.where` context, or with the wrong intent, is incorrect; no response in a matching context is a **miss**, logged as `response.evaluated {intent: null, correct: false, rt_ms: null}`. `response.timeout` is emitted when `timeout` elapses with no response (the timer starts at the onset of the first accepting phase) and ends the trial.
  - `trial.end.outcome`: timeout; without a `correct` rule completed / none; with one incorrect (any wrong response or miss), else correct, else none.
  - `on_response: end` ends the sequence at the first accepted response; `continue` keeps presenting. A phase with no duration must be able to end by a response or timeout, otherwise building the block throws a descriptive error.
  - Feedback phases are built for every outcome key and shown only for the actual outcome.
- **instructions:** pages loop in one node; `back` steps back; `min_time` shows the page in a no-response phase first (a second `phase.onset` without a stimulus field, so stimulus triggers fire once). Pages that name a stimulus report it in `phase.onset`.
- **`any` fires for every key down and tap, whatever else they are bound to** (found by the example: SPACE is bound to `go` in the experiment scope, which used to swallow `any` and stall instruction pages). The semantic event says whether the real key was consumed; the bridge injects a synthetic key for a tap or a consumed key, and leaves an unconsumed real key to reach jsPsych itself.
- **Hint lookup** for `{{intent.hint}}`: the current scope first, else the first block that declares the intent (the example search instructions use `{{next.hint}}`, declared by the next block).
- **Consent screen:** one survey with the markdown text, an agree/decline decision, and a checkbox per statement (only shown after agreeing; required unless `required: false`). `mode: attested` changes the wording only. The text is rendered with a small safe Markdown subset (`markdown.js`; author text is escaped first).
- **Built-in forms:** `subject_id` (BIDS label, `sub-` optional), `sex` (radio buttons: male / female / other / n/a, relabel via overrides), `age` (digits or `n/a`); session form `session_id` (default `01`). Likert questions are pinned to button mode (SurveyJS otherwise switches to a dropdown on small screens). `show_if` becomes a SurveyJS `visibleIf` expression (`regex` and `glob` operators are not supported in forms and throw).
- **M3 bug fixed here:** `input.js` called `setPointerCapture` on every press, which retargets the browser `click` to the stage and made every form unclickable; explicit capture is removed (pressed mouse and touch pointers keep delivering events anyway).
- **Boot:** the bundle supplies the generated schemas (`boot({schemas})`), so the framework has no path into `spec/`. The project is fetched, patched (debug overrides), compiled in the browser (Ajv, `new Function`: see the M1 CSP note) and custom stimulus generators are discovered from the `type` values in `stimuli.yaml` and imported from `custom/stimuli/<type>.js`. Compile errors are shown on the page instead of starting.
- **Not implemented (deliberately, listed so nothing is assumed):** custom tasks (`custom/tasks`, L2) and plugins (L3); `consent.require_scroll`; `form.data` extras on `form.submitted` (the event schema has no field for them); survey `allow_skip`; eye tracking and camera consent screens (M9); trigger sinks (M5). Audio stimuli render an `<audio autoplay>` element and are untested.
- **Browser tests** now have a global setup that rebuilds the bundles before every run (a reused server could otherwise serve stale code).

## 2026-10-01 - M5 triggers and relay

- **Raw templates are hex bytes.** The spec said raw bytes go "through the sink's template (e.g. `{value:02x}`, `AA {value:02x} 55`)" without saying whether that is ASCII text or bytes. I read it as space-separated hex byte tokens, so `"AA {value:02x} 55"` sends the three bytes `AA`, value, `55`, and no template sends the single value byte. Placeholders other than `{value:02x}` / `{value:x}` / `{value:X}` are rejected by the compiler (`bad-sink-template`). The reset byte goes through the same template.
- **New dependency decisions:** none added. The relay's WebSocket server is written by hand (`cli/ws-server.js`, RFC 6455: handshake, text/binary, fragmentation, ping/pong, close, 1 MiB limit) so the CLI needs no `ws`. The serial driver for real hardware is `serialport`, loaded on demand by the relay and **not** in `package.json` (users install it where the relay runs; it is a native module).
- **Spec change:** `sink.sync.offset_ms` may be `null` (a plain `ack` round trip has no clock offset). Schema regenerated.
- **Value resolution failures** map onto the catalog's drop reasons: a `{from}` / `{map}` that finds nothing gives `error`; a negative or non-integer value, or a raw value above 255, gives `out_of_range`. A raw sink drops an oversized value while a text sink in the same rule still receives it.
- **Engine semantics (mine where the schema is silent):** every matching rule fires (priority order, then definition order); `allow_multiple` only silences the compiler warning. `once` is once per session, kept across scope changes. Rules never see `trigger.*` / `storage.*` events (no loops). `{from}` paths read the event's data (plus `block`, `trial`, `phase`) first, then the session context (`subject.*`, `session.*`, `device.profile`). `trigger.sent.t_sent` is the hand-off time to the transport, taken just before the write, not the queue time.
- **Sink behaviour:** queue per sink with `min_gap_ms` (sink value, else `triggers.defaults.min_gap_ms`) and `max_queue` (256); a new trigger cancels a pending reset write; a failing write marks the sink `disconnected` and drops everything queued. WebSocket sinks reconnect with doubling delays (100 ms, 200 ms, ... up to `reconnect.max_delay_ms`) and mark themselves connected again; serial and USB sinks do not reconnect (they would need a new user gesture).
- **Ping sync protocol (mine):** `{"ping": id, "t": ms}` out, `{"pong": id, "t": receiver_ms}` back; `offset_ms` = receiver time minus page time from the round trip with the smallest delay; the relay answers with wall-clock milliseconds, so against the relay the offset is about the page's time origin. Plain acks are matched first-in-first-out.
- **Lifecycle order:** device resolved (pure) -> connect trigger sinks (only for a device that will be admitted) -> start recording. Status events raised while connecting are kept and replayed right after `session.clock_anchor`. A required sink that cannot connect and is cancelled ends the session with status `sink_failed` and **no recorded events and no record**; an optional one gives `sink.status error` plus `system.warning sink_unavailable`. The session record lists the sinks and whether each connected (`sinks.trigger`).
- **Deviation: a required sink lost mid-run stops the session with an error** (`system.error`, `session.end` reason `error`, record status `error`) instead of pausing. `spec/` says "the experiment pauses"; pause-and-reconnect needs a modal screen on top of a running jsPsych timeline, which I did not build. Say if that matters before real data collection.
- **Trigger scopes:** the lifecycle applies the block scope before `block.start` (so rules on `block.start` fire) and disables triggers after `block.end`; `response_task` applies the trial scope per trial and restores the block scope after it.
- **Tests:** fake Web Serial / WebSocket / WebUSB for the transports; a manual fake clock and scheduler (`tools/fake-time.js`) for queue timing; an in-memory virtual serial pair (`tools/virtual-serial.js`) for the relay; a Chromium test injects a fake `navigator.serial` and runs the whole example against it plus a real relay, checking that each rule's count and value match the example (172 triggers).

## 2026-10-01 - M6 local storage and recovery

- **The local log (`storage/local.js`, the only IndexedDB user).** Database `cndlpsych`, two stores: `sessions` (record, status, `last_seq`, `updated_at`) and `events` (key `[session, seq]`). Appends are buffered and written every `storage.local.flush_ms` (default 2000), or when 200 events are waiting, or when the page is hidden (see below). Each flush is **one transaction that writes the events and advances `last_seq`**, so what is on disk is always a gap-free prefix `0..last_seq`; a crash loses at most the events since the last flush and can never leave a hole. This is tested against real IndexedDB, including many flushes under load.
- **Nothing is stored before consent.** The database is created on `begin(record)`, which the lifecycle calls only after consent, forms, the `min_age` check and the device decision. Looking for old sessions (`findUnfinished`) does not create the database (it checks `indexedDB.databases()` first). Tests assert that no `cndlpsych` database exists on the consent, subject and session screens, after declining, and after a failed `min_age`.
- **Recovery recovers data; it does not resume the experiment.** Before consent the runtime looks for sessions still `in_progress`. `storage.local.recovery`: `offer` (default) asks per session: *Download its data* / *Delete it* / *Keep it for now*; `auto` closes and downloads every one without asking; `off` leaves them alone. Closing a session writes its record as `status: aborted`, `end_reason: aborted`, `last_seq` = the last event that reached disk and `ended_at` = the time of the last write (not the recovery time). I did not append a synthetic `session.end` event: its timestamp would come from a different page clock. The recovered download is `recovered_<subject>_<session>.zip`. Sessions that ended normally (complete, error, device_rejected) are never offered.
- **Export on finish (`storage/export.js`).** `export_on_finish` `jsonl` and `csv` are written into **one zip** (`<subject>_<session>.zip` with `session.json`, `events.jsonl`, `events.csv`) so a participant or experimenter gets a single file. The zip writer is hand-written (store only, CRC-32) and checked by an independent reader (`tools/unzip.js`, CRCs verified with Node's `zlib`). `bids` is not available until M8: it is skipped and the log gets `system.warning export_format_unsupported`. `file_access` (File System Access API) is **not implemented**.
- **Page lifecycle events** (`page.visibility`, `page.focus`) are now emitted from `input.js`, the one module that listens to the DOM; it also offers `onLeave(handler)` (visibility hidden, `pagehide`), which the lifecycle uses to flush the store. A flush started while the page is going away is best effort in browsers; the timed flush is the guarantee.
- **Degraded mode.** If IndexedDB is unavailable (some private modes) or a write fails, the store keeps every event in memory, reports `storage.status degraded`, and still exports; recovery is then impossible for that session. The store always keeps an in-memory copy of the events (a few MB for a normal session); revisit when gaze data arrives (M9).
- **`storage.status`** events (`opening`, `ready`, `degraded`) are logged after `session.start`; `closed` is deliberately not logged (it would come after the last event the record counts). With `storage.local.enabled: false` the in-memory store is used and nothing is recoverable.
- **Retention (my choice, please confirm).** Finished sessions stay in the browser's IndexedDB; there is no "manage local data" screen and no automatic deletion. For a participant's own device this means their identifiers remain stored locally after a session. The alternatives are deleting after a successful export, or deleting after upload (M7). Recovery also means the next person on a shared lab computer is shown an unfinished session of the previous participant (its id and counts); use `recovery: off` or `auto` for shared machines.
- **Tests:** the local store runs against real IndexedDB in Chromium (round trip, timed flush, gap-free prefix, abandon/remove, several sessions, no database creation on query, degraded mode). The crash tests use a **real SIGKILL of the whole browser** with a persistent profile (`tools/e2e/hard-kill.js`) and a new browser on the same profile: the log recovered after a kill during a trial is a gap-free prefix identical to what happened, losing under about 200 ms of events. `Page.crash` could not be used: in headless Chromium it takes the whole browser with it.

### M6 not verified

## 2026-10-02 - M6 follow-up: local data manager and resuming sessions

Requested after M6: a screen to remove stored sessions (per session, with select all), and resumable aborted sessions. This changes two M6 decisions: recovery no longer means "data only", and the retention gap now has a screen.

- **Resume = continue the same session.** Same participant, session answers, seed and device kind, on the same experiment files. The log carries on at `last_seq + 1` (`bus.startRecording({fromSeq})`), so there is no gap and no repeat. Completed blocks are skipped; the interrupted block restarts at its first unfinished trial (non-trial blocks such as instructions and surveys start over); the trial that was running **starts again from its beginning**, so its `trial.start` appears twice (once for each attempt). The seed makes block and trial order identical, which the browser test proves by comparing every oddball trial's letters with an uninterrupted run. A block's `block.start` already in the log is not written again.
- **What can be resumed:** records with status `in_progress` (interrupted), `aborted` (closed by recovery) or `error` (for example a lost required sink). Sessions that ended on their own (`complete`, `device_rejected`) cannot. Resuming is refused, with the reason on screen, when the experiment files changed (the `spec_hash` differs; note it also covers `debug` overrides), when the device is a different kind than the one recorded (`device.profile`; a `debug.simulate_profile` override counts), or when the saved log is incomplete. Trigger sinks are connected again first (a required one that fails leaves the saved data unchanged).
- **Clock.** A resumed page has a new time origin, so `t` restarts. The log gets a `session.clock_anchor` and a new `session.resume` event (spec change: new catalog event `{from_seq, time_origin_ms, wall_iso, block_id, trial}`), and the session record gets a `resumes` list (spec change: new optional array in `session.schema`). For events after `at_seq`, wall time is `time_origin_ms + t` of that entry. Exporters (M8) must use the anchors; a session can be resumed more than once (tested twice).
- **Not restored:** trigger `once` state and input-rule state start fresh; the interrupted trial's earlier events stay in the log (they are the first attempt). Resume needs the local store (IndexedDB), not the in-memory store.
- **Where to resume.** Start-up offer: an interrupted session now shows *Resume this session* first (when resumable), then download / delete / keep. `recovery: auto` still only downloads. The local data screen can resume any resumable session, including ones already closed as aborted by a download.
- **Local data screen (`?manage=1` on the experiment page, e.g. `play.html?manage=1`).** Lists every session stored in the browser, newest first, with subject, session, status (finished / interrupted / aborted / stopped by an error / device not allowed), start time and event count. One checkbox per session plus SurveyJS's built-in **Select all**; the actions are *delete* (always behind a confirmation that lists the sessions and says it cannot be undone), *download* (one zip each) and *resume* (exactly one). It records nothing, changes nothing until an action is confirmed, and is not linked from the participant screens: whoever runs the experiment opens it by address. It is built from the survey plugin, so no new DOM listeners.
- **Retention (the M6 question) is now answerable by the experimenter,** not decided by the framework: finished sessions still stay until removed on that screen. There is no automatic deletion.
- **Bug found and fixed (from M6): the persisted log began with `storage.status`, not `session.start`.** The local store's status replay was emitted right after recording started, ahead of `session.start`. M6 tested that ordering only with the in-memory store. Storage status is now logged after `session.start` and `session.clock_anchor` (after `session.resume` on a resume), with a regression test on the real store.
- **Play page** now uses the real local storage (`?memory=1` for in-memory), so these features can be tried by hand.

### Follow-up not verified

- Resume was exercised with a real browser kill (Chromium on Windows), the interrupted-tab path, a changed experiment, and the manager; the **different device kind** refusal is unit-tested only (a real phone and desktop sharing a profile is not possible).
- Resuming a session with trigger sinks was not run end to end (the sinks are removed in these tests); the connect step is the one already tested for new sessions.

A distributed bundle that contains it (the user-facing `cndlpsych/` folder in M10) would have to be offered under GPL-compatible terms; the framework's own licence has not been chosen. **Decision needed before M10 bundles it.** Nothing in this repository ships WebGazer except through `import('webgazer')` in `pipeline/gaze.js`.
- **Lazy by construction.** `pipeline/gaze.js` imports WebGazer only inside `loadWebgazer()`. The browser test bundle is now built with code splitting, so WebGazer is its own file; a test asserts that with eye tracking off neither that file nor the face model is requested, and with it on they are fetched only after the participant pressed Start.
- **Face model files are not on a CDN.** WebGazer looks for MediaPipe's face model at `./mediapipe/face_mesh` next to the page; the files are in `node_modules/webgazer/dist/mediapipe/`. The tests point it at the repo copy. **M10's user bundle must ship these files** (about 10 MB) or labs will have no eye tracking offline.
- **What WebGazer is not allowed to do.** `saveDataAcrossSessions(false)` (no calibration kept in the browser), its mouse listeners are removed unless `learn_from_clicks: true`, prediction dots / face overlay hidden. The real-WebGazer test checks `localStorage`, `sessionStorage` and that no `localforage` database appears.
- **Calibration is by fixation, not clicking.** The raw-listener rule means only `pipeline/input.js` hears clicks, so each dot is shown for a fixed time and its position is given to WebGazer as the truth while the participant looks at it (700 ms settling, then 900 ms of training at 10 Hz per dot; `calibration.points` 5/9/13 in a seeded order per repeat). Validation uses points between the calibration points (`validation.points`, at most 9).
- **Validation numbers.** For each point: accuracy = distance from the dot to the median prediction; precision = RMS scatter of the predictions. `mean_error_px` is the mean accuracy over points that had at least 3 predictions; if fewer than half of the points had data the validation fails and reports the stage diagonal as the error (the worst case, not a measurement). `gaze.validation.max_error_px` is the threshold used. The session record keeps `{attempt, mean_error_px, passed, at_trial}` per validation.
- **`on_fail`** (my reading of the schema): `retry` re-calibrates and re-validates up to `max_retries` times, then ends the session as `aborted`; `continue_flagged` does the same retries, then carries on with `passed: false` recorded; `abort` ends the session at the first failure. A camera that cannot be opened follows `camera.on_denied` (`abort`, or `continue_without` with `camera_denied: true` in the record), for any failure, not only a refusal; a `system.warning` `camera_unavailable` is logged either way.
- **Re-validation (`revalidate.every_trials` / `every_minutes`) runs at block boundaries only**, before the next block, never inside one; a failed re-validation follows `on_fail` and, when it ends the session, ends it as `aborted`.
- **What is recorded.** `gaze.samples` rows `[t, x, y]` in stage coordinates, at `sample_hz` (a throttle on the engine's own rate), from the first block until the session ends, in chunks of at most 200 rows (about 6 kB, checked against the smallest allowed storage chunk limit of 10000 bytes) or every second; `gaze.lost` after 500 ms without a prediction and `gaze.regained`; `input.gaze.dwell` (fixation inside `dwell.radius`, default 80 px, for `dwell.min_ms`, default 100) only while a block runs, with the target under the gaze. Gaze is not written during calibration screens. WebGazer does not expose camera frame times, so `t` is the time of the callback.
- **Order in the session.** After the device is admitted and the consent / form events are logged, before the first block. The camera consent statement is added by the compiler (existing behaviour). A resumed session calibrates again.
- **BIDS.** Gaze is **not** written to the BIDS dataset yet; it is complete in `sourcedata/.../events.jsonl`. BIDS 1.10 has an eye-tracking data type that needs `_physio.tsv.gz` + `_physioevents` conventions; deferred, because WebGazer samples are screen predictions without camera timestamps and the mapping needs a decision.

## 2026-10-08 - Frame-locked phases

- **What changed.** `pipeline/frames.js` is one animation-frame loop that runs "after n frames" jobs. A phase (`authoring/modules/phase.js`) no longer uses jsPsych's `trial_duration` timer: it counts `round(duration / frame time)` frames (at least 1) from the frame in which it was painted, and ends inside that frame's callback by calling `jsPsych.finishTrial()`. jsPsych then starts the next phase in microtasks of the same callback, so the next stimulus is drawn before the browser paints that frame. The onset of a phase that starts inside a frame callback is stamped with that frame's timestamp, and `phase.offset` now carries the same timestamp as `t`. A phase that starts outside a frame (after a response) is stamped with the next frame, as before. The response timeout in `response_task` is counted in frames from the onset frame of the phase that opens the window.
- **Targets are timestamps, not callback counts**, and a phase is aimed at its own actual onset: a late frame lengthens that phase by a frame and delays what follows by that much; it does not shorten the next phase or accumulate rounding.
- **A finding that changed the design: late callbacks keep an old timestamp.** When the page was blocked, Chromium ran the callback late but still passed the timestamp of the frame it was meant for, so timestamps alone showed no lateness (an 80 ms block left every flash at exactly 250 ms and 15 frames, while the next flash really lasted only 10). `frames.js` therefore moves every timestamp on by the whole frames the callback ran late (`now - timestamp`), for the stamps, for aiming later targets and for `frames`. After that fix the blocked flash reads 19-20 frames and the next one 15.
- **Zero-length gaps are no longer phases.** `post: 0` used to cost a timer tick and now costs nothing (a gap phase would cost at least one frame).
- **Spec change** (`events.catalog.yaml`, regenerated): `phase.onset.planned_frames` and `phase.offset.frames`; a phase whose `frames` differs from its `planned_frames` had a late frame. The `t` of `phase.onset` / `phase.offset` is a frame timestamp, which is the *start* of a frame and can be a few ms earlier than events emitted before it in the same callback (order by `seq`).
- **Measured** (headless Chromium, one Windows machine, 300 flashes of 6 frames + 6 frame gaps, `docs/timing.md`): stimulus duration minus planned was median +11 ms (max +31) with timers and is now within ±0.1 ms (the timestamp resolution); the rhythm error was median +17 ms (max +67) and is now within ±0.13 ms; 0 of 300 flashes had a late frame in the last runs (one earlier run showed a single late frame in the rhythm). **This says the software schedule is frame-exact on that machine. It does not say when light leaves a screen.**
- **Not done from the design discussed.** Phases are not built in advance (the next stimulus is built and drawn inside the same callback), images are not decoded in advance, and audio is not scheduled on the audio clock. A heavy stimulus can therefore make a frame late; this is stated in `docs/timing.md`. Phases without a duration, and instructions pages, still use timers.
- **Tests.** `frames.test.js` (fake display: targets by timestamp, half-frame tolerance, dropped frames, chained phases last their frames, cancel, frame timestamp visible to microtasks until the next macrotask); `frames.e2e.js` on the example's flash block at real speed (every flash lasts its planned frames, each phase starts with the timestamp the previous one ended with, the rhythm is whole frames). The full browser suite passed unchanged apart from the new test.

### Frame-locking not verified

- No photodiode: that the frame boundary the software chose is the frame in which light changed on a real display is the premise, not a measurement.
- Only 60 Hz headless Chromium on Windows. 120 / 144 Hz displays, variable refresh rate, phones and tablets (including browsers that throttle frames), Firefox and Safari were not tried.
- Late frames were provoked in a browser by blocking the page for 120 ms across the end of a flash (`frames.e2e.js`, passed 4 of 4 repeats on one machine); other causes of late frames (garbage collection, heavy stimuli, slow devices) were not.

## 2026-10-18 - Webcam recording (`webcam` in experiment.yaml)

New top-level key `webcam` (spec change, regenerated; the key was asked for): `enabled`, `profiles` (default every device), `audio`, `video {width, height, fps, facing}`, `bitrate_kbps`, `save`, `chunk_s`, `on_denied: abort | continue_without`.

- **How:** `pipeline/webcam.js` records the camera (and microphone if asked) with the browser's MediaRecorder for the whole session. The recorder hands over what it has every `chunk_s` seconds (MediaRecorder cannot stream without that); the pieces are appended, in order, to one WebM file (MP4 where that is all the browser has), which is one playable file.
- **Where the video goes (`save`):** `file` writes straight to a file on disk that the participant or experimenter picks in the browser's save dialog at the start (`showSaveFilePicker`, Chrome and Edge on a computer; `storage/video-file.js`). ## 2026-10-20 - `rt_from`: a response is to one particular stimulus of a sequence (oddball response times)

In an oddball sequence the response is to one stimulus (the second Ǝ) but the participant answers while a later letter is already on screen (a letter lasts 200 ms, a typical response takes 350-600 ms). Response times were measured from the stimulus showing when the key was pressed, so they were from the wrong letter, and a response in the 300 ms gap between letters was ignored altogether. New optional trial key `rt_from` in `response_task` (a predicate over `stimulus`, `phase`, `occurrence`, `index`, `trial` and the trial's conditions, the same as `correct.where`; spec change, regenerated; the key was asked for). When it is set:

- once the matching stimulus has appeared, **every response from then on is to it**: the time is from its onset (`response.evaluated.rt_ms`, so the BIDS `response_time` too) and `correct.where` is evaluated for it, whichever later letter or gap is showing. `response.evaluated` names that stimulus and occurrence;
- a response before it has appeared is to what is showing, has no response time (`n/a`) and is incorrect;
- responses are accepted in the gap after each accepting stimulus and in the gap after the trial, and the first one ends the trial (`on_response: end`);
- if the matching stimulus appeared and there was no response at all, one miss (`response.evaluated`, `correct: false`, no time) is reported when the trial ends, not one per phase.

Without `rt_from` nothing changes (times from the stimulus showing, responses in gaps ignored). Known limit: there is no upper bound on the time after the target, so a response several letters later is still correct; add a response window if that matters. Tested in `cli/rt-from.e2e.js` (response in the gap, while the next letter shows, before the target, none, and in the gap after the last letter). The visual search project uses it for its oddball block.
